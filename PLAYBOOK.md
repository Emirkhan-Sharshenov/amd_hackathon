# Плейбук: от kickoff до сдачи

Главный принцип: **оценка автоматическая и буквальная**. Одно неверное имя поля или статус-код = проваленный тест.
Поэтому фабрика должна быть устроена так, чтобы несоответствующая спеке работа **не могла пройти дальше**.

## T+0 — kickoff (сб 09:00 PDT / 16:00 UTC)

1. Скачать всё сразу: оба пакета задач, 4 спецификации, 4 тест-сьюта, харнесс. Закоммитить как есть в `inputs/` (не редактировать).
2. Выбрать трек/задачи. Критерии: насколько полно тест-сьют покрывает спеку, насколько детерминирован харнесс, сколько работы.
3. Запустить харнесс на пустом проекте — убедиться, что он работает локально и понятно, как читать его вывод. **Это первый артефакт фабрики.**

## T+1ч — извлечь контракт

Не отдавать спеку агенту-строителю «как текст». Сначала превратить её в проверяемый чек-лист:

- каждый endpoint / команда / экран → точный путь, метод, вход, выход
- каждое имя поля, enum, статус-код, текст ошибки, ID элемента — **дословно, с копированием**, без перефразирования
- инварианты (сохранение сумм, неотрицательность, идемпотентность и т. п.)
- граничные случаи: пустой ввод, битый JSON, повторный запрос, конкурентные запросы, большие числа

Каждая строка чек-листа ↔ ссылка на тест в сьюте (или пометка «тестом не покрыто — проверяем сами»).

## T+2ч — собрать банду в BAND Desktop

- Мандаты из [`mandates/`](mandates/) — generic-мандаты, копируются без изменений.
- **Всё предметно-специфичное (поля, коды, ID) живёт в спеке/чек-листе задачи, а не в мандатах.** Мандат описывает только: что роль владеет, как передаёт работу, что отклоняет.
- Модели: мощная модель для планирования/ревью, быстрая кодовая модель для строителя. Проверить 2–3 кандидатов через `scripts/featherless_smoke.py` и выбрать по качеству на реальной задаче, а не по названию.
- Handoff через `@mention`, адресат определяется по участникам комнаты, а не захардкожен.

## Цикл работы фабрики

```
architect ──план/срез──▶ builder ──код──▶ spec-warden ──ok──▶ verifier ──ok──▶ architect (verdict)
                             ▲                 │                  │
                             └──── reject ─────┴──── reject ──────┘
```

- Маленькие срезы: один endpoint/фича за раз, каждый заканчивается зелёным прогоном тестов.
- Регрессии: после каждого среза прогоняется **весь** сьют, а не только новые тесты. Баллы не должны падать.
- Отклонение всегда с конкретикой: какой пункт чек-листа, ожидалось X, получено Y.

## Тест на generic-мандат

> Отдай мандат команде, которая строит **что-то совсем другое**. Он всё ещё имеет смысл?

Если в мандате есть имя поля, URL, статус-код, ID элемента, название сущности из задачи — это не generic. Вынести в спеку.
